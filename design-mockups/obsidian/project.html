The problem

Every plugin started with the same lost day.

A Figma plugin is two programs that can't see each other. One runs in a sandbox with access to the document; the other runs in an iframe with access to the DOM. They speak only by passing messages, and neither can be served from disk the way an ordinary web app can.

So every plugin begins by wiring a bundler, a manifest, a message bridge, and a build step that inlines the UI. Change one line and you rebuild and reload by hand. I had assembled that same toolchain enough times to stop pretending it was a one-off.

Shape of a project

manifest.json

What Figma reads

Declares the two entry points and the permissions. Generated and kept in sync.

src/main.ts

The sandbox

Document access. No DOM, no network, no bundler assumptions that hold anywhere else.

src/ui.tsx

The interface

An ordinary front-end app in React, Svelte or Vue. This is the half that reloads.

The approach

Treat it as an ordinary front-end project.

Plugma hides the two-program problem underneath. One command scaffolds, one develops, one ships. The framework is your choice, because the tool sits under the framework rather than beside it.

The part worth having is real hot module reloading. Edits appear without a rebuild and without losing plugin state, which turns interface work from a stop-start loop into something continuous — the single biggest difference to how the work actually feels.

Constraint

The sandbox can't be served from disk, so the UI has to be inlined at build time. Most of the work was making that invisible during development without changing what ships.

Since

Plugma became the substrate for everything after it — the later plugins listed on this site are all Plugma projects.

Outcome

The setup it replaces took most of a day. It now takes a command.

Plugma is used by plugin developers across the Figma community and is still maintained.
