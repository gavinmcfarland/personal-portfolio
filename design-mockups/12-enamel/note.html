Two programs, one plugin

A Figma plugin looks like one thing and behaves like two. Almost every difficulty in building one comes from that gap, and almost every tool that helps is a tool that hides it.

§1 The split

When a plugin runs, Figma starts two separate programs. The first runs in a sandbox with access to the document — nodes, selection, pages — and no DOM at all. The second runs in an iframe with a full DOM and no access to the document whatsoever.

They cannot call each other. They cannot share objects. Everything that crosses between them is a message, serialised on the way out and parsed on the way in.

§2 What that costs

The obvious cost is ceremony. Any behaviour that spans both halves needs a message type, a sender, a listener, and a shape agreed in two places at once:

main.ts
// sandbox half — document access, no DOM
figma.ui.onmessage = (msg) => {
  if (msg.type === 'resize') {
    figma.ui.resize(msg.w, msg.h)
  }
}

The less obvious cost is the development loop. Neither half can be served from disk the way an ordinary web app can, so the UI has to be inlined into the built file — and every edit means a rebuild, a re-run, and the loss of whatever state you were testing against.

§3 The fix

Plugma puts all of that underneath a single command. In development the UI is served from a dev server and pointed at by the manifest; at build time the same UI is inlined into the output. The sandbox half never notices the difference, so hot module reloading works the way it does anywhere else — edits appear without a rebuild, and without dropping the plugin state you were testing against.

Interface work stops being a stop-start loop. That is the whole return on the tool, and the substrate for every plugin I built after it.
